## Run protocol

**Goal order:** (1) the rail, end-to-end against the SANDBOX broker on the test key, behind flags, merged; (2) one US broker at a time, each a config row + quirks + fixtures + a flag-gated beta; (3) the two Indian brokers under their own flags; (4) crypto on the same rail. Read-only throughout. Trading is reserved, not built (Appendix C).

- **Branch A — `feat/MONEY-<A>` (P18, one PR):** rail foundation. Merge when `yarn verify:push` is green; the SnapTrade production-access application runs in parallel and is not a merge gate — everything ships flag-off.
- **Branch per broker — `feat/MONEY-<broker>` (P19–P29, one PR each, small):** starts after A merges. A broker PR never touches the rail's shared modules except to add its config row and a fixture; if it must, that is a rail bug and gets its own commit with a `-logic` test first.
- **Branch B — `feat/MONEY-<B>` (P30, one PR) then one PR per exchange (P31–P33).**

Create Linear tickets from the session (Cowork's Linear link was down on 12-Sep): "SnapTrade rail foundation", one per broker "SnapTrade: <Broker>", "SnapTrade crypto foundation".

**House rules (every prompt assumes them):** `-logic.ts` pure functions with real-file fixtures; `{ isSet: false }` arms on EVERY new Prisma field (Mongo `db push` creates indexes, never fields — MONEY-1050/1205/1234/1236 — write that test first); `finite()` guards on every money/quantity field (`fixing-bugs` skill: NaN/Infinity/Invalid-Date poison — SnapTrade documents `price`, `units`, `cost_basis`, `cash`, `buying_power` as nullable); injectable deps at every I/O seam (SnapTrade client, Redis, Prisma, Pub/Sub, clock); no fail-open gates (entitlement, flag, HMAC — a missing env var is a closed gate, tested); IDOR tests on every route that takes a connection/authorization/account id; apps/web server action + apps/api v1 mirror ship together with route tests (P14's rule); flags present-and-`"false"` in both cloudbuild specs; `TEST-COVERAGE.md` + `workers/CLAUDE.md` + `scripts/README.md` + `docs/env-vars-reference.md` per change; new Mongo collections listed in the PR description (these are user-data collections, not reference data — they do NOT go into `sync-prod-to-qa.sh REFERENCE_COLLECTIONS`, say so); `writing-tests` layers (unit / contract / functional / route); `/code-review` before the PR; never weaken a test to pass.

**Facts settled by research — do not re-litigate in-session (evidence: the plan doc §2, every line sourced):**

- Plan = Pay-as-you-go **Real-time**, $2/connected user/month; "connected user" = one end user with ≥1 completed connection, however many brokers; **disabled connections bill until deleted**; failed connections never bill.
- Legacy `GET /accounts/{id}/holdings` returns **410 for signups after 11-May-2026** — never call it. Use `/positions/all`, `/balances`, `/orders`, `/recentOrders`, `/activities`.
- Real-time = pull-through to the broker on request. **Transactions are delayed 1 day on all plans.** Manual refresh is disabled on real-time plans except when the connection's `data_freshness_mode` is `delayed` (Vanguard, IBKR), and then it is billed per call.
- **Polling rules SnapTrade checks at launch review:** ≤4 background Holdings calls/day/user, or once per end-user login + set intervals while active; activities ≤1 call/account/24h; spread daily jobs; poll only the endpoint a webhook names. **250 requests/minute per client**, `X-RateLimit-*` headers, 429 body says when to retry.
- Webhook `Signature` = HMAC-SHA256(raw body, consumerKey); retries 3× from 30 min; no IP allow-list. Events: CONNECTION_ADDED/BROKEN/FIXED/DELETED/UPDATED/FAILED/ATTEMPTED, NEW_ACCOUNT_AVAILABLE, ACCOUNT_REMOVED, ACCOUNT_HOLDINGS_UPDATED, ACCOUNT_TRANSACTIONS_INITIAL_UPDATE, ACCOUNT_TRANSACTIONS_UPDATED, USER_REGISTERED/DELETED, TRADE_DETECTION/TRADE_UPDATE (not used).
- Portal: `POST /snapTrade/login` → `redirectURI` valid **5 minutes**; body `broker`, `connectionType: "read"`, `customRedirect`, `reconnect`, `connectionPortalVersion: "v4"`; redirect returns `status=SUCCESS&connection_id=…` | `ERROR&error_code=…&status_code=…` | `ABANDONED`. `userId` must be immutable and not an email; `userSecret` is returned once.
- Developer terms: market data from SnapTrade is for **that end user only**, may not be stored, resold or redistributed. Positions `price` and `/currencies/rates` are display-only for that user. Databento + Tiingo remain the platform's price sources; SnapTrade never feeds `Candle`, quote caches, screeners, alerts or research tools.
- Activities: `startDate` omitted ⇒ "the first transaction known to SnapTrade based on `trade_date`"; `limit` default and max 1000 + `offset`; reverse-chronological; the activity ID "_can_ change if the transaction is deleted and re-added" → content hash is the second key. Orders `days` default 30, capped at 90; per-broker windows in Appendix A.
- Positions (`/positions/all`): `instrument.kind` enum is `stock | option | crypto | future | etf | mutualfund | cef | adr | cfd | other`; `instrument.exchange` is a NULLABLE STRING ("Exchange MIC code or exchange code for the security"), not an object; `cash_equivalent` is a boolean on the position; `price`, `units`, `cost_basis` nullable; `tax_lots[]` when the broker exposes them.
- `ACCOUNT_HOLDINGS_UPDATED` "is sent once per day when holdings are updated" and "is primarily useful for Daily plans because Real-time plans refresh supported holdings data when it is requested" — act on it only for `data_freshness_mode: delayed` connections.
- Launch-guide trading item is EITHER/OR: "either clear user consent for automated trading or an order-confirmation flow that shows all available impact, fee, and commission information".
- Per-broker capabilities/history are in Appendix A (copied from SnapTrade's Institution Support page on 12-Sep-2026). Config rows are copied from there, not remembered.
- Existing repo facts: `Holding`/`Trade`/`Position`/`Order`/`MutualFund` have NO `currency`; `SYNC_ENABLED_BROKERS` = Zerodha only; MONEY-841 64-shard fan-out; `FxRate` exists (`pair`, `date`, `rate`, `source`) written by `us-eod-sync`; `UsInstrument.openFIGIComposite` exists; PostHog flags via `apps/web/lib/actions/feature-flags.ts`; `requireFeature` in `apps/web/lib/actions/premium-gate.ts`; founder allowlist precedent `apps/web/lib/brokers/connect-gate.ts`; OAuth state helpers `packages/core/src/brokers/oauth-state.ts` (10-min TTL); encryption `getEncryption()` from `@usemoney/security`; consent at connect = `ConsentRecord` kind `AI_ADVISORY`; failure log = `apps/web/lib/brokers/failure-log.ts` → `BrokerIntegrationFailure`.

## Appendix B — Per-broker verification protocol (template for docs/reference/snaptrade-broker-verification.md)

For each broker, in order, with dates and counts: (1) sandbox path green on the test key (rail-level, once); (2) contract fixtures golden (mapper tests) for this broker's row; (3) flag-gated beta: slug added to the master payload for named users only; first connect → account list (categories, raw types) → positions (kinds seen vs Appendix A) → balances (currencies) → orders (count, window observed) → activities (earliest trade_date vs expected horizon; types observed) → 24 h later: activities pulled once, background holdings pulls ≤ 4, no 429s → forced disable → email + NEEDS_REAUTH → reconnect → cleared; (4) open the slug to all paid users; (5) record any Appendix A cell the beta contradicted and fix the config row in a docs-only commit.
