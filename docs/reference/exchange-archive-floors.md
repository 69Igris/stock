### 14b.5 — Market Pulse: a scheduling bug that would 404 forever, invisibly

`nse-market-pulse` has **zero archived objects**, and the reason is not the one
the registry anticipated.

The family is `enabled: true`, `provenance: "p2-probed"`, and its notes record a
real ranged-GET probe returning 206 for six consecutive months. It is also the
only DATED family with `cadence: "monthly"`, so the only pass that can fetch it
is `report-archive-monthly` (`0 8 3 * *` — the 3rd of each month, 08:00 IST).

**Why nothing is archived yet:** the family was added on 2026-08-14 (commit
`32398532`), eleven days *after* the 3-Aug run. It has simply never had a turn.
First opportunity: 3-Sep-2026.

**Why that turn will fail, and keep failing.** Simulated against the real code
(`resolveTargetDay` + the family's own `buildUrl`):

```
run 2026-09-03 08:00 IST -> targetDay 2026-09-03
   URL: .../web/mediaattachment/2026-09/Market_Pulse_September_2026.pdf
run 2026-10-03 08:00 IST -> targetDay 2026-10-01
   URL: .../web/mediaattachment/2026-10/Market_Pulse_October_2026.pdf
```

On the 3rd of month M the job asks for month M's issue. By the registry's own
note, *"the issue reviews the month just ended, so the current month 404s until
it appears."* So every monthly run asks for a PDF that does not exist yet.

The dangerous part is not the 404 — it is that this 404 is **indistinguishable
from the two causes the family already documents** (not-yet-published, and the
differently-named special editions). A reader seeing it would conclude the known,
expected condition had occurred, and the family would sit at zero objects
indefinitely with nothing in the logs contradicting that reading.

This is the MONEY-1194 shape again: a cron reasoned about when to RUN and not
about which file exists on the day it runs.

**Why the obvious fix is wrong.** "Shift the monthly pass back one month" would
break the four other monthly families. `nse-mf-approved-*` are UNDATED and
`rolling: true` — their URL carries no date and always serves the current month,
so the archive key is deliberately the FETCH month. Shifting them would stamp the
current month's bytes with the previous month's key: silent mis-filing, which is
exactly the corruption the `rolling` / `backfillable` docs exist to prevent.

So the fix has to be per-FAMILY, not per-cadence. Two candidates:

1. A `publishLagMonths?: number` field on `ReportFamily`, honoured by
   `report-archive-sync` when it resolves the target day. Self-documenting, and
   it makes the asymmetry between dated and rolling monthlies explicit.
2. Let `nse-market-pulse.buildUrl` resolve to the PRIOR month. Smaller, but it
   makes `buildUrl(d)` mean "the issue published around d" rather than "the file
   FOR d", which is inconsistent with every other family.

Recommend (1). **Not applied here** — `report-registry.ts` was being rewritten
concurrently by 14a.0 in this same branch, and a second editor in that file is
how a merge silently drops a registry row. Filed as a follow-up.

Consequence for 14b.5 as scoped ("monthly PDFs → `StockDocument
docType:market_pulse, symbol:_MARKET` → the existing extract→embed chain"):
there is nothing to wire a parser onto, because there are no bytes and none will
arrive until the scheduling bug is fixed. The task's own instruction — *"if it
404s, record and move on"* — is satisfied, with the correction that it is not
really 404ing yet; it has never been asked.
