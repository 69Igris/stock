## 1. SnapTrade in our terms

SnapTrade is an aggregator: the user authenticates with their broker inside SnapTrade's hosted Connection Portal, SnapTrade holds the broker tokens, and we read normalised data through one API with our client credentials plus a per-user secret. That makes it a **rail**, not another adapter of the kind that lives in `packages/core/src/brokers/adapters/`: the existing `BaseBrokerAdapter` contract (`getAuthUrl` → `authenticate` → `refreshAccessToken` → `fetch*` with per-connection credentials) assumes we hold the token, refresh it and call the broker. Under SnapTrade we hold none of that. The mapping between SnapTrade's vocabulary (docs.snaptrade.com/docs/terminology) and ours:

| SnapTrade term                           | Definition (verbatim, terminology page)                                                                                                                           | Our model                                                                                                                               |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| SnapTrade User                           | "A user record under your API key that represents one of your end users and authorizes access to that user's SnapTrade data."                                     | New `SnapTradeUser` row: one per UseMoney user, holds the encrypted `userSecret`                                                        |
| Connection (brokerage authorization)     | "An authorized link between a SnapTrade user and one brokerage login that grants data access and optionally trading access."                                      | New `SnapTradeAuthorization` row: `type` read/trade, `disabled`, `disabled_date`, `data_freshness_mode`                                 |
| Account                                  | "A specific brokerage account under a connection that SnapTrade exposes for balances, holdings, activity, and trading."                                           | One `BrokerConnection` row per account (`brokerUserId` = SnapTrade `accountId`) — the grain every downstream table already keys on      |
| Position / Balance / Order / Transaction | as documented                                                                                                                                                     | `Holding` (+ raw table for derivatives/crypto), new `BrokerCashBalance`, `Order`, new `BrokerActivity` ledger → `Trade`                 |
| Periodic Sync / Manual Refresh           | "The process where SnapTrade updates account data from the connected brokerage." / "An explicit API-triggered sync request … outside the periodic sync schedule." | Our sync engine calls read endpoints; the refresh endpoint is unavailable on real-time plans except for delayed-data connections (§2.5) |

Two facts from the FAQ shape the data model: "When you create a connection, SnapTrade will automatically sync all accounts under the set of credentials to the brokerage", and "Deleting the connection will remove all accounts under that connection" — you cannot delete one account, only hide it on your side. So the authorization is the unit of connect/repair/delete/billing, and the account is the unit of sync and display.

### 2.1 Pricing, plans and billing

From snaptrade.com/pricing (page and its FAQ, expanded in the browser today): Starter is $0 for "5 connected accounts" with real-time data and trading; Pay as you go Real-time is "$2 per connected user / month, includes trading"; Pay as you go Daily is "$1 per connected user / month, with optional read-only with manual sync ($0.05 per sync)"; Custom plans add "Higher rate limits" and dedicated support. ### 2.5 Freshness, polling rules and webhooks

Real-time on SnapTrade means pull-through, not push: "Real-time plans refresh supported holdings data when it is requested" and "Supported holdings endpoints fetch the latest data from the brokerage when called" (docs/syncing, docs/realtime-data). Transactions are the exception on every plan: "Transactions are delayed 1 day on all plans" (pricing FAQ); "transactions are cached, updated once per day with the daily sync, and delayed by one day", and "If you need intraday trade activity, compare orders with transactions" (docs/syncing). The account-data guide contrasts the two: orders "Is updated intraday", include "cancelled orders and pending orders", often have "more granular timestamps than account activities" but "Only looks back a few months at most"; activities "are updated once daily", "only contain transactions that resulted in a change of position", "may not have timestamps of when the transaction occurred", and often have "years of history for the account". The manual refresh endpoint "is disabled for Real-time plans (Personal and Pay as you go) unless SnapTrade uses delayed data for the connection" — check `data_freshness_mode` — and "Each call to this endpoint incurs an additional charge"; it is asynchronous and completes with an `ACCOUNT_HOLDINGS_UPDATED` webhook. Daily-sync timing "is not consistent at the same time every day, but guaranteed once per day" (FAQ).

The launch guide's pre-production checklist is binding and sets the sync engine's budget, quoted verbatim: "You don't call the Holdings API more than 4 times per day per user in the background, or more frequently than once per end-user login and at set intervals while the user is actively using your app." "You don't call the activities (transactions) endpoint more than once per account every 24 hours for an account." "If you run a daily job to pull data, you spread the calls out as much as possible over the period." "If your app uses webhooks, you poll the API correctly (using the proper endpoint and payload data) in response to the specific webhook type received." Rate limit: "Every SnapTrade client is ratelimited to 250 requests per minute by default" (pricing FAQ; the rate-limiting doc states the same 250 per minute), enforced globally across endpoints with `X-RateLimit-Limit / -Remaining / -Reset` headers and a 429 body such as "Expected available in 7 seconds" (docs/ratelimiting); Custom plans raise it. The checklist also requires a user-visible way to view and delete connections; a disabled-connection flow with "at least one method of detection and one way to notify users (such as in-app notifications or emails)"; and for trading (later) "1 trade per connected account per second" plus "either clear user consent for automated trading or an order-confirmation flow that shows all available impact, fee, and commission information".

Webhooks (docs/webhooks): USER_REGISTERED, USER_DELETED, CONNECTION_ATTEMPTED, CONNECTION_ADDED, CONNECTION_DELETED, CONNECTION_BROKEN, CONNECTION_FIXED, CONNECTION_UPDATED, CONNECTION_FAILED, NEW_ACCOUNT_AVAILABLE, ACCOUNT_TRANSACTIONS_INITIAL_UPDATE ("when we complete the initial transactions sync after a new account is connected"), ACCOUNT_TRANSACTIONS_UPDATED, ACCOUNT_REMOVED, ACCOUNT_HOLDINGS_UPDATED, TRADE_DETECTION, TRADE_UPDATE. Payload carries `webhookId`, `eventTimestamp`, `userId`, `eventType`, `connectionId`, `brokerageId`, `accountId`, `details`. Security: "The `Signature` header contains an HMAC SHA256 hash of the request body, using your consumer key as the key." Delivery: "exponential backoff (starting at 30 minutes) until it is either delivered successfully, or 3 retry attempts have been made"; a response that is not 200, 201, 202 or 204 counts as undelivered; no IP allow-list. The listener URL is configured in the dashboard. `ACCOUNT_HOLDINGS_UPDATED` "is sent once per day when holdings are updated" and "is primarily useful for Daily plans because Real-time plans refresh supported holdings data when it is requested" (docs/syncing); the webhooks doc adds that it is sent on the daily account syncs and after a manual refresh.

### 2.6 Data-use constraints

Developer Terms of Use, verbatim: the client agrees "that any market data passed over the SnapTrade API will only be used to serve the End User for which that data is licensed by their broker" and "That they will not store, resell, or redistribute Market Data passed over the SnapTrade API"; "To delete all End User data passed through the SnapTrade API upon request from the applicable End User or SnapTrade"; "Not to mine, re-sell, or re-package any End User data obtained via the SnapTrade API to third parties without the express written consent of both the End User and SnapTrade." The terms are silent on AI/LLM processing; the 1-Sep report's guidance stands — consent in-flow, purpose limitation, disclose Gemini/Claude as sub-processors, no training on user data — and the personal-agent consent design in `data-platform-decision-plan-v1-sep2026.md` (DPDP Rules, purpose-specific consent) covers the same data once it reaches the lake.

## 3. Live data: SnapTrade versus Databento + Tiingo

The question was whether an authenticated SnapTrade connection can supply live market data, or whether the existing Databento + Tiingo stack is enough for analysis. The answer is the second, for three independent reasons.

First, the licence. The developer terms quoted in §2.6 forbid storing or redistributing market data received through SnapTrade and restrict its use to "the End User for which that data is licensed by their broker". A position's `price` may be shown to that user as their broker's valuation; it may not enter `Candle`, the quote cache, screeners, alerts, the research agent's tools, or any surface another user sees. Second, the mechanism. Real-time on SnapTrade is pull-through to the broker, budgeted at four background holdings calls per user per day plus once-per-login and "set intervals while the user is actively using your app", with 250 requests per minute for the whole client; there is no stream. The only quote endpoint, `GET /accounts/{accountId}/quotes` (max 10 symbols per call, equities only), says of itself: "The quotes returned can be delayed depending on the brokerage the account belongs to", it is "not a substitute for a market data provider", and "Frequent polling of this endpoint may result in the disabling of your keys." Third, coverage. It prices only what the user holds or asks about through a connected account — nothing for watchlists, indices, options chains, history or backtests.

What the repo already has covers the analysis needs. For the US, `tiingo-realtime` (workers/src/realtime) holds the IEX websocket for "everything a user watches" — top-of-book, mid-derived bars, no volume — and Databento is "the source of backtest-grade US intraday truth: consolidated, TRADE-derived bars carrying real volume" (docs/reference/databento-harvest-runbook.md); Tiingo EOD and corporate actions complete the daily layer, and `UsInstrument` carries `openFIGIComposite`, which is exactly the FIGI join SnapTrade recommends for matching positions to instruments. For India, prices come from the exchange archive (bhavcopy) and Yahoo at runtime, with the paid Kite Connect live path dormant in `workers/src/connect` (MONEY-837) and the `federated-data` flag reserved for per-user broker quotes; a SnapTrade connection to Zerodha or Upstox adds nothing to that path. For crypto (phase 2), the exchanges' own public feeds are free to call but not ours to display — Coinbase's Market Data Terms forbid it outright, Kraken and Backpack require written consent, Binance's API terms are unpublished and its policy bars commercial use without written authorisation — so the platform source must be a licensed aggregator; Tiingo's crypto endpoints qualify only if the Display-Redistribution order form covers crypto, which its public pricing page does not (13-Sep-2026 addendum `crypto-venues-live-data-and-multi-asset-sep2026.md`).

What SnapTrade does add is the broker's own statement of the account: quantities, cost basis, tax lots where the broker exposes them, cash per currency, and the broker's last price at sync time. The design keeps that as `brokerPrice` / `brokerValue` on the user's rows and prices the portfolio for analysis from our own instrument prices, so the two can be shown side by side ("broker value" versus "market value") and the gap doubles as a staleness indicator for daily-data brokers like Vanguard and IBKR.

## 4. Architecture

### 4.1 Rail abstraction and broker identity

Two ways to model a SnapTrade-connected broker were weighed. Reusing the institution's existing `BrokerType` value (e.g. `ZERODHA`) with a `rail` column would keep the enum small but would put SnapTrade and direct rows under the same `broker` filter in `Holding`, `Trade`, `Position`, `MutualFund`, `SyncLog`, `BrokerIntegrationFailure`, the FIFO pairing worker, the holdings de-duplication logic and the mobile API — every one of which keys on `broker` today — and the per-broker flags Shaswat asked for would then need a second discriminator everywhere. The repo already solved this once: `ZERODHA_CONNECT` (MONEY-837) is "a distinct broker value so its token lives in its own BrokerConnection row, separate from the free Personal app". The plan follows that precedent.

Each (institution, rail) pair is a `BrokerType` value. Brokers with no direct adapter take the plain institution name — `ROBINHOOD`, `ETRADE`, `VANGUARD`, `PUBLIC`, `WEBULL`, `TASTYTRADE`, `MOOMOO`, `ETORO`, later `COINBASE`, `KRAKEN`, `BINANCE`; brokers that already have a direct rail take a suffix — `ZERODHA_SNAPTRADE`, `UPSTOX_SNAPTRADE`, `INTERACTIVE_BROKERS_SNAPTRADE`. `BrokerConnection` gains `rail` (`DIRECT` default, `SNAPTRADE`), and `BROKER_CONFIGS` gains `rail`, `snaptradeSlug`, a `capabilities` block copied from the matrix in §2.3 and a `historyPolicy` block (`activities: "ACCOUNT_OPEN" | { years } | "NONE"`, `orders: { days, executedOnly }`, `activityTimestampGranularity: "day" | "second"`, `dataFreshness: "realtime" | "daily"`). Those two blocks are what make the per-broker prompts thin: they configure, they do not re-implement.

The adapter contract splits in two. `BaseBrokerAdapter` stays for the direct rail. A new `SnapTradeAdapter` implements a narrower `ReadPort` (`listAccounts`, `fetchPositions`, `fetchBalances`, `fetchOrders`, `fetchRecentOrders`, `fetchActivities(startDate, endDate, page)`) plus a `TradingPort` interface (`previewOrder`, `placeOrder`, `cancelOrder`) whose methods throw `TradingNotEnabledError` until the trade phase; the SnapTrade client is one class parameterised by slug, so a broker prompt adds a config row, mapping quirks and fixtures, never a second HTTP client. The factory returns the rail-appropriate adapter from `BROKER_CONFIGS[broker].rail`.

### 4.2 Data model changes

New collections: `SnapTradeUser` (one per user: minted immutable `snaptradeUserId`, AES-256-GCM `encryptedSecret/iv/authTag` via `@usemoney/security`, `registeredAt`, `deletedAt`); `SnapTradeAuthorization` (one per connection: `authorizationId` unique, `broker: BrokerType`, `slug`, `type` read/trade, `disabled`, `disabledAt`, `dataFreshnessMode`, `deleteAfter`, `lastWebhookAt`, `brokerageEnabled`); `BrokerActivity` (the raw normalised ledger: every activity type from §2.4 with `activityId`, `contentHash`, `currency`, `amount`, `units`, `price`, `fee`, `fxRate`, `tradeDate`, `settlementDate`, `externalReferenceId`, `symbolRef`, `derivedTradeId`); `BrokerCashBalance` (per account per currency: `cash`, `buyingPower`, `asOf`); `BrokerRawPosition` (phase-1 parking for `instrument.kind` option / future / crypto arriving from equity brokers, and any unmapped kind: raw JSON, `kind`, `symbol`, `units`, `currency`, `asOf`). Existing collections gain columns: `BrokerConnection` adds `rail`, `railAuthorizationId`, `railAccountId`, `institutionAccountId`, `accountCategory`, `accountRawType`, `accountCurrency`, `dataFreshnessMode`, `connectionType`; `Holding`, `Trade`, `Position`, `MutualFund`, `Order` add `currency` (ISO-4217; a one-off backfill stamps `"INR"` on every direct-rail row except `INTERACTIVE_BROKERS`, whose direct mapper starts writing the position's own currency in the same PR), `rail`, `externalInstrumentId` (SnapTrade universal symbol id), `figi`, `brokerPrice`, `brokerValue`, `priceAsOf`; `Trade` adds `provisional` (a fill seen only in orders, not yet in activities) and `activityId`.

Two repo rules apply to every new column and are written into the prompts as the first test: Mongo `db push` creates indexes, never fields, so every new field is absent on existing rows and every selection over one carries `{ isSet: false }` (MONEY-1050/1205/1234/1236); and money fields go through the `finite()` guards from the `fixing-bugs` skill, because a `null` `price` or `units` from SnapTrade (both are documented as nullable) is exactly the non-finite poison that skill catalogues. `exchange` is never defaulted to `"NSE"` on a SnapTrade row — the IBKR SMART-router incident in `packages/core/src/brokers/adapters/interactive-brokers.ts` shows what happens when exchange, "half of a match key", is guessed: a US `ACC` lot matched ACC Ltd on the NSE. SnapTrade positions carry `instrument.exchange` as a nullable string ("Exchange MIC code or exchange code for the security"), and an absent one is stored as the sentinel `"UNKNOWN"`, not a default.

The `FxRate` model already exists (`pair`, `date`, `rate`, `source` YAHOO/RBI, `@@unique([pair, date])`) and is written by `us-eod-sync`; the rail adds the pairs the brokers in scope introduce (USD to start; GBP, EUR, CAD, AUD when eToro/IBKR accounts report them) and a read-time converter in the dashboard/holdings logic that never rewrites native amounts. Indian tax on foreign assets uses a prescribed conversion (Rule 115, SBI TT buying rate) that differs from a market close — that belongs to the tax lane (`usemoney-tax-india` skill), not to this rail, and the plan says so rather than hiding it.

### 4.3 Connect flow

Web: the `/brokers` picker shows SnapTrade-rail cards when the master flag (and the broker's own flag, if any) is on and the SnapTrade brokerage catalogue says `enabled && !maintenance_mode`; a free-plan user sees the card locked with the upgrade CTA (`requireFeature` from `apps/web/lib/actions/premium-gate.ts`). The server action `startSnapTradeConnectAction(broker)` runs the entitlement gate, ensures a `SnapTradeUser` (register on first use, store the secret encrypted, never return it to the client), writes a signed state via the existing `generateOAuthState` (10-minute TTL, which comfortably covers SnapTrade's 5-minute link), calls `POST /snapTrade/login` with `broker: slug`, `connectionType: "read"`, `connectionPortalVersion: "v4"`, `customRedirect: <APP_URL>/api/brokers/snaptrade/callback?state=…`, and redirects the browser (full-page or new tab; the React SDK iframe is an option later, and the mobile flow needs the redirect anyway). The callback verifies state, reads `status`; on `SUCCESS` it fetches `/authorizations/{connection_id}`, upserts `SnapTradeAuthorization`, lists `/accounts`, filters to that authorization, upserts one `BrokerConnection` per account with `status: CONNECTED`, writes the AI_ADVISORY `ConsentRecord` the direct brokers already write at connect, and publishes the initial sync job; on `ERROR` it logs a `BrokerIntegrationFailure` row through the existing failure-log classifier; on `ABANDONED` it returns the user to the picker. Reconnect reuses the same action with `reconnect: authorizationId`, and the upgrade-to-trade path later is the same call with `connectionType: "trade"`.

Mobile: `apps/api` mirrors the action as `POST /v1/brokers/snaptrade/connect` (returns `redirectURI`) and `POST /v1/brokers/snaptrade/complete` (takes `connection_id`); the app opens the portal in SFSafariViewController / Chrome Custom Tabs, which the portal doc prescribes because "This preserves browser features required by OAuth and Passkeys", with `customRedirect` pointing at a universal link. The repo rule from P14 — a web action and its `apps/api` v1 mirror ship together with route tests — applies to every SnapTrade surface.

### 4.4 Sync engine

The scheduled path reuses the MONEY-841 fan-out unchanged: the daily `broker-sync` trigger shards by `syncBucket` and each leaf selects `SYNC_ENABLED_BROKERS`, which widens from `["ZERODHA","ZERODHA_CONNECT"]` to include every SnapTrade broker type. Inside a leaf, `classifyConnectionForSync` gains a rail branch: a SnapTrade connection is synced when its authorization is not `disabled` and its per-account call budget allows it; the credential-triple and token-expiry checks are direct-rail only, since SnapTrade rows carry no credentials of their own. `syncBrokerConnectionRow` dispatches on rail: the SnapTrade branch calls positions, balances and orders (`days` = the broker's `historyPolicy.orders.days`, capped at 90), maps them, and persists with the existing delete-and-`createMany` transaction for holdings and the existing upsert for orders; activities are pulled only if the account's last activities pull is older than 24 hours.

The call budget is the design's centre because SnapTrade's launch review enforces it. Per account per day the engine spends at most two background holdings pulls — one after the account's market close (US: 03:00 IST, after 17:30 ET; India: 16:30 IST), one before its open — leaving two for webhook-triggered pulls (`ACCOUNT_HOLDINGS_UPDATED`, `NEW_ACCOUNT_AVAILABLE`, `CONNECTION_FIXED`) so the four-per-day background ceiling holds even on a day with two webhooks. Foreground pulls follow the "once per end-user login and at set intervals while the user is actively using your app" clause: the holdings page triggers one pull per login session (a Redis key `st:login:{accountId}` with a 12-hour TTL) and re-pulls at a 15-minute interval while the tab is active, never on a timer when it is not. Activities are pulled once per account per 24 hours (Redis `st:act:{accountId}` TTL 24h) except in direct response to `ACCOUNT_TRANSACTIONS_UPDATED` / `_INITIAL_UPDATE`, which the checklist explicitly allows. All counters and the decision function live in a pure `snaptrade-budget-logic.ts` with tests, and the numbers are constants in one place so a Custom-plan uplift is a one-line change. A Redis token bucket caps the whole client at 200 requests per minute (below the 250 default to leave headroom for the web tier), the `X-RateLimit-Remaining` / `-Reset` headers are honoured, 429s back off with jitter, and `SYNC_CONNECTION_CONCURRENCY` (4) stays as the per-leaf fan-in. Daily-job calls are spread across the leaf's window rather than fired at once, as the checklist asks.

Webhooks land on a workers route (`workers/src/routes/snaptrade-webhook.ts`, Cloud Run, always reachable), verify the HMAC over the raw body with the consumer key, deduplicate on `webhookId` through the existing pubsub-dedupe TTL collection, acknowledge 200 immediately, and publish a `SNAPTRADE_EVENT` Pub/Sub message; a processor maps event → action: `CONNECTION_BROKEN` sets the authorization `disabled`, flips its accounts to `NEEDS_REAUTH`, starts the `deleteAfter` clock (now + 30 days) and creates the in-app notification plus the reconnect email; `CONNECTION_FIXED` clears all of that and pulls; `CONNECTION_DELETED` / `USER_DELETED` mark rows `DISCONNECTED`; `NEW_ACCOUNT_AVAILABLE` creates the account row and syncs it; `ACCOUNT_REMOVED` marks the account closed; the two transaction events trigger the budgeted activities pull; `ACCOUNT_HOLDINGS_UPDATED` triggers a budgeted holdings pull only for `data_freshness_mode = delayed` connections (Vanguard, IBKR) — on a real-time connection it merely mirrors SnapTrade's own daily sync, which our scheduled pull already supersedes, so acting on it would spend a reserved webhook pull for nothing. Because delivery is at-least-once and retries start 30 minutes later, every handler is idempotent and a nightly reconciliation (`/authorizations` + `/accounts` listing per user, spread across the day, at most one listing call per user per day) repairs anything a lost webhook would otherwise hide.

### 4.5 Historical sync — "as far back as the broker allows"

Depth is decided by the broker, not by us: the activities endpoint with no `startDate` defaults to "the first transaction known to SnapTrade based on `trade_date`", and the matrix in §2.3 gives the per-broker horizon (since account open for Robinhood, Public, tastytrade, Moomoo, Vanguard, Zerodha and the three exchanges; two years for E\*TRADE, Webull and IBKR; nothing for Upstox and eToro). The initial backfill therefore never sets `startDate` (the default is "the first transaction known to SnapTrade based on `trade_date`"): it waits for `sync_status.transactions.initial_sync_completed` (or the `ACCOUNT_TRANSACTIONS_INITIAL_UPDATE` webhook), then pages `limit=1000` / `offset` until `pagination.total` is reached — one logical pull, many pages — and records `first_transaction_date` on the account row so the UI can say "history from 14-Mar-2019" truthfully, or "this broker does not provide transactions" for Upstox and eToro. This generalises the existing Zerodha Console backfill (`syncHistoricalTradebook`, yearly windows to a ~10-year floor) without touching it.

Incremental pulls use `startDate = lastActivitiesSync − 7 days` to catch late-posted items and rely on idempotent writes: `BrokerActivity` is upserted on `(userId, broker, brokerUserId, activityId)`, and because SnapTrade warns that an activity ID "_can_ change if the transaction is deleted and re-added", a `contentHash` (account, type, symbol, trade_date, units, amount, currency) is the second key — an incoming row whose id is new but whose hash matches an existing row updates that row instead of duplicating it, the same role `Trade.duplicateHash` plays today. BUY and SELL activities derive `Trade` rows (`sourceType: SYNCED`, `brokerTradeId = activityId`, `needsRepairing: true` so the FIFO pairing worker picks them up); dividends, fees, interest, contributions and withdrawals stay in the ledger for the income and cash-flow views and are not trades. Day-granular brokers (Zerodha, Vanguard, Chase-class) get `tradeTime = null` and a `tradeDate`; the pairing logic must accept same-day buy and sell with no intraday order, and the prompt writes that test first. Option events, splits and transfers are stored but not interpreted in phase 1 (they land in the ledger with `derivedTradeId = null`).

Because transactions lag a day on every plan, the engine bridges the gap with orders: executed orders from `/recentOrders` and `/orders` that have no matching activity yet become `Trade` rows flagged `provisional: true`; when the activity arrives (matched on symbol, date, units and `external_reference_id` where present) the provisional row is replaced by the authoritative one. The holdings page can then show today's fills without misrepresenting them as settled ledger entries.

### 4.6 Portfolio sync correctness

Holdings are replaced atomically per account inside a transaction (the existing `persistHoldings` pattern), so a partially failed pull never leaves a mixed snapshot; a pull that returns an empty `results[]` for an account whose `sync_status.holdings.initial_sync_completed` is false is treated as "not yet synced", not as "sold everything". `account.status` closed/archived and `ACCOUNT_REMOVED` mark the row `CLOSED` and keep its history; `account_category` DEPOSIT and LOC accounts (Robinhood checking/savings, Fidelity credit cards in the future) are stored but excluded from the investment dashboard, and `null` is treated as INVESTMENT as the docs advise. A user with two brokerage logins at one institution has two authorizations and their accounts do not collide, because `brokerUserId` is the SnapTrade `accountId`; a user who connects the same Zerodha account both directly and through SnapTrade sees both rows, distinguished by rail, and the holdings de-duplication logic (`holdings-dedup-logic.ts`) learns the rail so the consolidated total counts the account once with the direct rail preferred when both are live.

Values are native. Each `Holding` row carries `currency`, the broker's `brokerPrice`/`brokerValue` with `priceAsOf`, and our own `currentPrice` from the instrument master where the FIGI/ticker match succeeds; unmatched instruments fall back to the broker price with a visible "broker-priced" marker. Portfolio totals are computed at read time in the dashboard logic as native per account, then converted with the `FxRate` row for the display date — never persisted converted — so a re-sync cannot rewrite history and FX moves show up as FX, not as P&L noise.

### 4.7 Flags, entitlements, cost and cleanup

Flags follow the `APP_FEATURE_FLAG_KEYS` pattern in `apps/web/lib/actions/feature-flags.ts` (PostHog-evaluated, default-false, kill switch): `snaptrade-brokers` (master, covers the US set), `snaptrade-zerodha`, `snaptrade-upstox`, and `snaptrade-crypto` in phase 2. The master flag's payload carries the enabled slug list so one broker can be pulled from the picker without a deploy; a broker is offered only when the master flag is on, the slug is in the payload, its own flag (if it has one) is on, and the SnapTrade catalogue reports it enabled and not in maintenance. `INTERACTIVE_BROKERS_SNAPTRADE` additionally respects the existing `us-broker-ib` flag so the two IBKR rails cannot both appear to a user who is not in that cohort.

Entitlement is a paid-plan gate (PRO/PREMIUM/ULTIMATE) enforced server-side in the connect action and its API mirror, with the founder allowlist bypass modelled on `connect-gate.ts`; a per-user cap of five authorizations bounds the worst case. The cost model is therefore $2 × (paying users who connected at least one SnapTrade broker that month), independent of how many brokers or accounts each links, plus nothing for API calls; the plan does not project a user count — that is measured, not assumed — but the per-user marginal cost is fixed and the gate keeps it inside a paid tier's revenue.

Cleanup is a nightly job: authorizations with `disabled = true` and `deleteAfter <= now` are deleted at SnapTrade (`DELETE /authorizations/{id}`) and their accounts marked `DISCONNECTED` (holdings snapshot cleared, trades and ledger kept — they are the user's history, and the developer terms' deletion duty is triggered by a user or SnapTrade request, which the existing account-deletion flow already honours by also calling `DELETE /snapTrade/deleteUser`); on day 23 the user receives the "reconnect or we'll unlink" email through the existing email preference system. The job runs before month-end by construction (nightly), which is what removes a stale connection from "the following month's invoice".

### 4.8 What is reserved now for trading later

Nothing in phase 1 places an order, but the seams are built so the trade phase is additive: `SnapTradeAuthorization.type` records read/trade per connection and the connect action accepts `connectionType` so an upgrade is the same portal call; `BROKER_CONFIGS[x].capabilities.trade` is filled from the matrix (Robinhood, Vanguard, IBKR, eToro, Zerodha, Upstox are `false` and stay so — SnapTrade offers no trading for them); `TradingPort` exists with `TradingNotEnabledError`; the `Order` model already has the fields the equity order impact/confirmation flow needs; and the checklist items the launch guide will ask about in a trading review ("either clear user consent for automated trading or an order-confirmation flow" showing impact, fee and commission data with estimates identified, one trade per account per second, opt-out and connection deletion) are listed in the prompts' "later" section so nobody designs them out. The equity-trading support table (order sizing, order types, time-in-force per broker) is on the Institution Support page and will be copied into config only when that phase starts, because the tax-lots doc warns that "Brokerage capabilities may change".

### 4.10 Capacity arithmetic (per user, no assumed user count)

Per connected account per day the background engine makes at most: 2 scheduled pulls × (positions + balances + orders + recentOrders) = 8 calls, 1 activities call (plus its pages), and at most 2 webhook-triggered pulls × 4 calls = 8; plus a nightly `/accounts` listing per user. That is about 17 requests per account per day at the ceiling, and typically half that. At 250 requests per minute (360,000 per day) the default limit supports tens of thousands of accounts before the Custom-plan uplift is needed; the binding constraint is SnapTrade's four-per-day background rule, not our throughput, which is why the budget logic is a first-class module.
